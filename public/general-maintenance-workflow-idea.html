💡 General Maintenance Workflow Idea

A shareable, step-by-step approach anyone can follow to keep their app secure and well maintained.

by Andrew D · Web Enthusiast · www.andrewdaugdaug.com

This is not just a technical setup guide. It is a thinking process. Before touching any tool or writing any instruction, you need to understand what you are protecting and why. The goal is simple: see everything working from your own eyes before automating it. If you cannot explain it, you are not ready to automate it yet.
🔄 The Process

Every good maintenance setup follows this cycle. Notice that testing appears twice — once before implementing, and once after. That is intentional.

⚠️ Most people skip straight to "Implement." That is how you end up with automation that runs but does nothing, or worse, does the wrong thing. Always document and test first.
📋 The Six Phases
🧠
Phase 1: Think
Start here

Before opening any tool, sit down and answer these questions:

  • What does my app actually do and who uses it?
  • What is my tech stack — what libraries and services is it built on?
  • What are the most sensitive parts of my app? (Passwords, logins, file uploads, payments?)
  • What could go wrong if one of my packages had a known vulnerability?
  • How often do I want to check? Daily, weekly?

For Spark, the tech stack includes Node.js, Express, JWT for auth, bcryptjs for passwords, Multer for file uploads, Socket.io for chat, and Supabase for the database. Each of these is a package written by someone else. Any of them could have a vulnerability discovered tomorrow.

You can find your tech stack listed in your app's package.json file or in your documentation. For Spark, it is documented in the Tech Stack section of the docs.
📄
Phase 2: Document (first time)
Write before you build

Write out what you want to happen in plain English. Not code. Not commands. Just words. This forces you to actually understand the process before trying to automate it.

  • What should the maintenance routine check?
  • What should happen when it finds something?
  • How will you be notified?
  • What is your approval process before anything gets updated?
  • What is the update process — local test first, then PR, then deploy?

For Spark, this became the Maintenance Workflow page — written entirely in plain English before a single routine was created. That page became the reference guide for everything that followed.

💡 Creating a documentation page first is not extra work. It is the work. If you cannot explain the process clearly enough to write it down, you do not understand it well enough to automate it yet.
🧪
Phase 3: Test (before implementing)
See it yourself first

This is the most important phase and the one most people skip. Before setting up any automation, manually go through the process yourself at least once so you can see exactly what happens.

  • Manually check your packages for updates — what does the output look like?
  • Manually create a test GitHub Issue — does the notification email arrive?
  • Apply a test update on a local branch — does the app still work?
  • Open a PR — what does the review process feel like?

For Spark, this meant running the routine manually before relying on the daily schedule. The first test revealed a critical discovery: remote cloud routines do not have npm installed, so the original instructions using npm outdated and npm audit silently failed. The manual test caught this before it became a habit of false confidence.

⚠️ If you skip this phase, you will set up automation that appears to work (green tick, no errors) but actually does nothing. You will only find out weeks later when you realize no emails ever arrived.
📄
Phase 4: Document (second time)
Update from reality

After testing, you will always discover something that was wrong or missing in your first draft. Go back and update your documentation to reflect what you actually learned.

  • Did the process work exactly as you described in Phase 2? If not, update it.
  • Did you discover any limitations? (Like: remote routines cannot run npm commands)
  • Did the notification email actually arrive? Was it at the right address?
  • Were there any steps that were unclear or needed more detail?

For Spark, this phase meant updating the workflow page multiple times: correcting the routine instructions to use web APIs instead of npm commands, fixing the email notification explanation, clarifying the branching process, and adding the direct GitHub issues link.

Good documentation is never finished on the first try. The second version, written after real testing, is always better than the first.
⚙️
Phase 5: Implement
Now automate it

Only now, after you have thought it through, documented it, tested it, and updated your docs, are you ready to set up the actual automation. At this point you are not guessing. You know exactly what you are building and why.

  • Set up the routine with the tested, corrected instructions
  • Connect the right repository
  • Set the schedule (daily at 9:00 AM)
  • Choose Remote so it runs even when your machine is off

Because you tested first, the instructions you paste into the routine are already proven to work. You are not experimenting with live automation — you are just scheduling something you already confirmed works.

🧪
Phase 6: Test (after implementing)
Confirm the automation works

After the routine is live, trigger it manually one more time to confirm the automated version behaves exactly the same as when you ran it manually in Phase 3.

  • Does the GitHub Issue get created with the right title and body?
  • Does the email arrive at the right address?
  • Does the scheduled run fire at the right time?
  • Is the Runs log showing green ticks?

Once you see the automated run produce the same result as your manual test, you can trust the system. From this point forward, it runs every day on its own and you only need to act when an email lands in your inbox.

This final test is your sign-off. It is the moment you go from "I think this works" to "I have seen it work with my own eyes."
🧪 Why Testing Appears Twice

Most workflows show testing only at the end. This one puts it in the middle too, and that is the key difference.

Phase 3 test (before implementing) Phase 6 test (after implementing)
You are the one doing the steps manually The automation is doing the steps for you
Catches problems before they get baked into automation Confirms the automation does what you manually confirmed works
You see the real output with your own eyes You verify the automated output matches what you saw manually
Builds your own understanding of the process Gives you confidence to trust the system going forward

This applies to any app, not just Spark

The tech stack will be different. The packages will be different. The tools might be different. But the process — Think, Document, Test, Document, Implement, Test — stays the same regardless of what you are building or maintaining. Share this page with anyone setting up their own maintenance workflow.
