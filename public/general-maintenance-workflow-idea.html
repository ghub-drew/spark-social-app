💡 General Maintenance Workflow Idea

A shareable, step-by-step approach anyone can follow to keep their app secure and well maintained.

by Andrew D · Web Enthusiast · www.andrewdaugdaug.com

This is not just a technical setup guide. It is a thinking process. Before touching any tool or writing any instruction, you need to understand what you are protecting and why. The goal is simple: see everything working from your own eyes before automating it. If you cannot explain it, you are not ready to automate it yet.
🔄 The Real Process

Based on what actually happened building the Spark maintenance system, the honest process looks like this. It is not six tidy phases. It is four steps with a fix loop in the middle.

🧠 Think
Understand first
→
📄 Document
Write it before building
→
⚙️ Implement
Set it up
→
🧪 Test
Run it, see what breaks
→
🔧 Fix + Document
Update docs with what you learned
→
🧪 Test again
Repeat until it works
💡 The Test → Fix → Document → Test loop is not a sign of failure. It is the actual work. For Spark, this loop ran more than 10 times before everything worked end to end. Every iteration taught something new and made the system more reliable.
📋 The Four Steps
🧠
Step 1: Think
Start here

Before opening any tool, answer these questions in plain language:

  • What does my app do and who uses it?
  • What is my tech stack: what libraries and services is it built on?
  • What are the most sensitive parts? (Passwords, logins, file uploads, payments?)
  • What could go wrong if a package had a known vulnerability?
  • How often do I want to check? Daily, weekly?

For Spark, the tech stack includes Express, JWT, bcryptjs, Multer, Socket.io, and Supabase. Each is written by someone else. Any of them could have a vulnerability discovered tomorrow.

Find your tech stack in your app's package.json or docs. For Spark, it is in the Tech Stack section of the documentation.
📄
Step 2: Talk to Claude, Claude documents it
You describe, AI writes

You do not write the documentation yourself. You describe what you want to Claude in plain English, conversationally, the way you would explain it to a friend. Claude then creates the documentation page for you.

The questions to answer are:

  • What should the routine check?
  • What happens when it finds something?
  • How will you be notified?
  • What is your approval process before anything gets updated?
  • What is the update process: branch, PR, Vercel preview, merge, git pull?

You do not need to know the answers in technical detail. Just describe the outcome you want. Claude figures out the how and puts it into a documentation page.

For Spark, this became the Maintenance Workflow page. Andrew never wrote a single line of it. He described what he wanted, Claude created the page, and it was updated by Claude every time something was discovered through testing.

💡 The actual documentation starts after the first implementation. The first version is based on what you think will happen. Every version after that is based on what actually happened. Claude updates it each time.
⚙️
Step 3: Implement
Set it up

Set up the automation based on your documentation. At this point you are making your best attempt based on what you know. You will not get everything right the first time and that is expected.

  • Set up the routine with the instructions you documented
  • Connect the right repository
  • Set the schedule (daily, weekly, whatever fits your app)
  • Choose Remote so it runs even when your machine is off
⚠️ Do not expect the first implementation to work perfectly. The next step (Test + Fix loop) is where the real learning happens. Implementation is just the starting point.
🧪
Step 4: Test, Fix, and Document. Repeat.
The real work

Run the routine manually. See what breaks. Fix it. Update your documentation. Run it again. Repeat until it works end to end with your own eyes.

For Spark, this loop uncovered these issues one by one, each fixed before the next was even visible:

  • Remote routines have no npm. The instructions used npm outdated and npm audit which silently failed. Fixed by switching to npm registry web APIs.
  • Claude's GitHub integration is read-only. It could not create issues. Fixed by creating a Personal Access Token (PAT) with repo scope.
  • GitHub does not email you about your own actions. The PAT authenticates as ghub-drew, so no email arrived. Fixed by adding a GitHub Actions workflow that posts a bot comment mentioning @ghub-drew on every new issue.
  • The Actions workflow failed on the first try. Missing permissions: issues: write. Fixed with a one-line addition.
  • The email only said "a new issue was opened." Not useful on its own. Fixed by having the bot comment include the full scan report body.

Two more things were discovered during the update process itself:

  • Localhost testing is not needed for package updates. Vercel automatically builds a live preview URL for every PR. That preview runs in the same cloud environment as production, making it more reliable than localhost. Localhost is still useful for major code changes where you want fast iteration without pushing to GitHub every time.
  • A temporary branch is always required before opening a PR. You cannot PR directly from main to main. The branch holds the proposed changes safely while you review. Once merged, the branch disappears.
  • git pull is the only step that flows GitHub → local. Every other step in the process goes local → GitHub. After merging a PR, GitHub and Vercel are already updated. git pull is what brings your local machine in sync.

Each fix was immediately documented in the workflow page. The documentation was updated 10+ times throughout this process. That is normal.

The loop ends when you see the full chain working with your own eyes: routine runs, issue is created, bot comments, email arrives with the full report, PR is opened, Vercel preview builds, you merge, cebuspark.com is live. That is your sign-off.

This applies to any app, not just Spark

The tech stack will be different. The tools might be different. But the process is always the same: Think, Document, Implement, then Test and Fix until it works. The loop is not a detour. It is the destination.
