🛡️ Maintenance Workflow

How Spark stays secure and up-to-date, automatically.

by Andrew D · Web Enthusiast · www.andrewdaugdaug.com

Think of this like a home security check. Every day, an automated assistant quietly inspects your app's packages and libraries, the building blocks your app runs on. If it finds anything that needs attention, it notifies you first. You review it, decide if you want to update, and only then does anything change. Nothing is ever updated without your approval.

STAGE 1 Daily Security Scan: Runs automatically, no action needed from you
▼
1

The scan wakes up at 9:00 AM every day

A Claude routine is scheduled to run every morning. It opens your project and starts checking everything. You don't have to do anything. Your computer doesn't even need to be on; this runs in the cloud.

2

It checks your packages for security issues

Because this is a remote cloud routine with no terminal access, it checks your packages using web APIs instead of running npm commands directly. It does two things:

  • Outdated versions: reads your package.json from GitHub, then checks the npm registry API for the latest version of each package
  • Security vulnerabilities: checks the npm security advisory database for known CVEs affecting your installed versions

It focuses on your most critical packages first, the ones that handle passwords, logins, and file uploads.

3

It always creates a GitHub Issue and notifies you

Whether updates are found or not, the routine always creates a GitHub Issue in ghub-drew/spark-social-app using a Personal Access Token (PAT). This gives it write permission to open issues even as a remote cloud agent.

💡 How the email notification works: GitHub will not email you about actions performed by your own account (the PAT authenticates as ghub-drew). To get around this, a GitHub Actions workflow is set up in the repo. The moment any new issue is opened, the Actions bot automatically posts a comment mentioning @ghub-drew. That comment, coming from a different identity (the Actions bot), triggers a real email to andrewsdlc@gmail.com.

You can also check issues directly at any time: github.com/ghub-drew/spark-social-app/issues

4

If issues ARE found, it creates a report and emails you

The routine opens a GitHub Issue in your repo with a clear summary: what package, what the risk is, and what version to upgrade to. GitHub then automatically sends that to your email (andrewsdlc@gmail.com) because you are the repo owner. No extra setup needed.

STAGE 2 Update Run: Only starts when you manually trigger it
▼
1

You receive the email and decide which updates to approve

The email from github-actions[bot] contains the full scan report. Review it and decide which packages to update. You do not have to approve everything. Skip low-priority items and focus on the critical ones first.

You can also check the issue directly at: github.com/ghub-drew/spark-social-app/issues

2

Tell Claude to apply the updates and open a PR

Open Claude Code in your project folder and type:

"Apply the security updates from GitHub Issue #[number]. Create a branch, apply the updates, push to GitHub and open a PR."

I will handle all of this in one go:

  • Create a temporary branch (e.g. security/june-2026-updates): you cannot open a PR directly from main, a branch is always required first
  • Apply the package updates on that branch, not on main
  • Push the branch up to GitHub
  • Open a PR from that branch into main on GitHub
💡 Direction is always local → GitHub, never the other way around. Your local machine sends the branch up. GitHub receives it. The PR is a GitHub-only thing comparing two branches. Your local machine never receives a PR. It only ever sends code up.
3

Vercel automatically builds a preview URL

The moment the branch is pushed, Vercel detects it and builds a live preview of the app with the updates applied. You will see it in two places:

  • Your Vercel dashboard under Active Branches, click Preview
  • A comment posted by Vercel directly inside the GitHub PR

The preview URL is temporary and only exists while the PR is open. It is not cebuspark.com. It is a separate test URL running the updated packages in the same cloud environment as production.

The PR is not live yet. Nothing touches cebuspark.com until you click Merge.
4

Review the PR diff and test the preview URL

Open the PR on GitHub at github.com/ghub-drew/spark-social-app/pulls. You will see:

  • The diff: exactly which package versions changed in package.json
  • The Vercel preview link: posted as a comment in the PR

Click the preview URL and test the app. Log in, browse, send a message. If everything works the same as before, you are ready to merge.

5

Merge the PR. Vercel deploys automatically.

Click Merge pull request on GitHub. That is all. There is no separate push step.

Merging into main is what triggers Vercel to deploy. Within 1-2 minutes cebuspark.com is live on the updated packages. The preview URL disappears once merged.

6

Run git pull to sync your local machine

After merging, your live site and GitHub are already updated. But your local machine is still on the old version. Run this:

git pull origin main
💡 This is the only step where the direction is GitHub → your local machine. Everything else in this process flows local → GitHub. This step is the reverse: it downloads the merged changes from GitHub and brings them down to your machine so everything is in sync.

Localhost testing is more valuable when making major code changes (new features, bug fixes) where you want to iterate quickly without waiting for Vercel to build each time, or when you need to debug something with live console logs.

🤔 Why Does This Matter and Why Daily?
▼

Every package your app uses is written by other developers. When they discover a bug or security hole in their code, they release a fix, a new version. If you don't update, your app keeps running the broken version, and hackers who know about that weakness can exploit it.

⚠️ Real example: In 2022, a vulnerability was found in jsonwebtoken that let attackers forge login tokens, meaning someone could log in as any user without a password. Apps that updated within days were safe. Apps that didn't stayed exposed for months.

The goal of this maintenance routine is to make sure you always know within 24 hours when something like that happens, and you can fix it with a single click.

Why run it daily and not weekly or monthly?

Security vulnerabilities are published publicly the moment they are discovered. That means the same day a weakness is announced, attackers already know about it and start scanning for apps that haven't patched yet. The longer your window between scans, the longer you are exposed without knowing it.

Scan frequency Max days exposed before you find out Verdict
Daily 1 day Best
Weekly 7 days Acceptable
Monthly 30 days Risky
Manual only Unknown, whenever you remember Risky

Daily is also low noise. Most days the scan runs, finds nothing, and you get a quiet "All Clear" email. It only becomes urgent when something real is found. You are not being interrupted every morning for no reason. You are just keeping a 24-hour safety net running in the background.

Spark handles real user accounts, passwords, login tokens, and file uploads. These are exactly the things attackers target. A daily check means you are never more than one day behind on protecting your users.
📖 Git Concepts: pull vs merge vs PR vs fork
▼

These four terms are often confused because they sound similar. Here is the plain English difference between each one.

git pull local command

A command you run in your terminal. It downloads the latest changes from GitHub and applies them to your local machine automatically in one step.

Think of it as: "Go check GitHub and bring me whatever is new."

git pull origin main
git merge local command

A command you run in your terminal. It combines two branches together on your local machine. It does not touch GitHub at all.

Think of it as: "Take the changes from this branch and fold them into the branch I am currently on."

git pull = git fetch + git merge combined. When you run git pull, it first downloads from GitHub (fetch) then merges those changes into your local branch automatically. That is why pull is the command you use most often.
Pull Request (PR) GitHub concept

A PR is not a command. It is a request you make on GitHub asking someone (or yourself) to review and approve changes before they get merged into the main branch. It lives entirely on GitHub, not on your local machine.

Think of it as: "Hey, I made some changes on this branch. Can you review them and pull them into main when you are happy?"

There are two common scenarios:

  • Branch to Main (same repo): you create a branch, push it, open a PR into main. This is what we do for security updates in Spark.
  • Fork to Original (cross-account): you fork someone else's repo, make changes, and open a PR back to their repo. Common in open source.
Fork GitHub concept

A fork is a full copy of someone else's GitHub repo saved under your own GitHub account. You use it when you want to contribute to a project you do not own.

Think of it as: "Make me a complete copy of this repo under my account so I can make changes without touching the original."

We do not use forks in the Spark maintenance workflow. Everything stays within ghub-drew/spark-social-app using branches.

Term Where it happens What it does Used in Spark?
git pull Your terminal (local) Downloads and applies GitHub changes to your machine Yes, after merging a PR
git merge Your terminal (local) Combines two local branches together Indirectly (git pull uses it)
Pull Request GitHub (remote) Asks for review and approval before merging a branch Yes, branch to main for updates
Fork GitHub (remote) Copies someone else's repo to your account No
❓ Common Questions
▼
What if I'm busy and don't act on the notification right away?
That's fine. The report stays in your GitHub Issues until you're ready. Check anytime at github.com/ghub-drew/spark-social-app/issues. The next day's scan will also re-check and remind you if there are still outstanding issues. Critical vulnerabilities will be flagged more urgently.
What if an update breaks my app?
Because updates are applied on a separate branch, your main branch and your live site are never touched. If something breaks during local testing, just tell me to delete the branch and that's it. Nothing was harmed. You start fresh when you're ready to try again.
Can I skip updates I don't want?
Yes. You're in control. You can close a GitHub Issue to dismiss a low-priority update, or tell me to skip specific packages. Only what you approve gets touched.
Will this touch my database or user data?
No. This routine only updates the code packages your app uses. It never modifies your Supabase database, user accounts, messages, or photos.
What's the difference between a security vulnerability and an outdated version?
A security vulnerability is a confirmed exploit. Someone has found a way to attack apps using that package version. That's urgent. An outdated version just means a newer release exists, but there may be no known attack yet. The scan flags both, but you should always prioritize the security vulnerabilities.

REQUIRED Personal Access Token (PAT): needed for issue creation
▼

Why it is needed: Claude's built-in GitHub integration only has read-only access to issues. To create issues the routine needs a PAT with write permission.

Steps to create it:

1

Go to github.com/settings/tokens

2

Click Generate new token (classic)

3

Name it Spark Security Scan, set expiry to 1 year, tick the repo scope only

4

Click Generate token and copy it immediately. GitHub only shows it once.

5

Paste the token into the routine instructions where it says [YOUR_PAT_TOKEN]

⚠️ Keep the token private. Do not commit it to GitHub or share it publicly. It only lives inside the Claude Code routine instructions.
