Step 3 June 3, 2026

A screenshot changed the direction

Andrew shared a screenshot of Claude Code's Routines panel, the interface for setting up automated scheduled agents. The question was: how should a maintenance routine be structured so that security updates are checked automatically, but nothing is ever applied without approval?

Three requirements were on the table:

  • Check all tech stack packages for new security updates
  • Send an alert when updates are found
  • Wait for approval before doing anything
💡
Step 4 June 3, 2026

The two-stage approach was proposed

Rather than one routine trying to do everything, a split design was recommended. Stage 1 runs on a schedule and only scans. It never changes anything. Stage 2 only runs when Andrew manually triggers it after reviewing the findings.

The key insight: routines cannot pause and wait for human input mid-run. So the approval gate had to be a completely separate action, not a step inside the same routine.

✅ Two-stage split: scan first, update only on approval
One routine that scans and updates automatically

Step 7 June 3, 2026

The branching process was clarified

Andrew asked a smart question: should the update process go from GitHub down to local, or the other way around? The answer was the other way: always local first, then GitHub, then Vercel. Never the reverse.

This led to a fuller explanation of the branching approach:

  • Updates are applied on a new local branch, not on main
  • Andrew tests the app at localhost:3000 on that branch
  • If it passes, the branch is pushed and a GitHub PR is opened
  • Andrew merges the PR, and Vercel auto-deploys
  • If anything breaks locally, the branch is deleted and nothing is harmed

Step 8 June 3, 2026

Local vs Remote was decided

When Andrew opened the Routines panel and saw the Local / Remote choice, the answer was clear: Remote. A Local routine requires the computer to be on and Claude Code to be running at exactly 8 AM. A Remote routine runs in the cloud regardless of whether the machine is on or not.

✅ Remote: runs in the cloud at 8 AM daily, no matter what
Local: requires machine to be on and Claude Code open

Step 9 June 3, 2026

The maintenance system is ready to set up

After all the planning, refining, and documenting, the maintenance workflow is fully designed and ready to activate. The copy-paste instructions for the Stage 1 routine live inside maintenance-workflow.html under the Setup section.

The final system in plain English:

  • Every day at 9 AM, a remote Claude routine scans your packages for vulnerabilities
  • It always opens a GitHub Issue, even if everything is clean, so you get email confirmation the scan ran
  • You review the issue, then open Claude Code and say what to update
  • Updates go on a new local branch, you test at localhost, then approve the PR
  • Vercel deploys automatically once the PR is merged

Step 12 June 3, 2026

Testing revealed three important discoveries

Multiple manual test runs were triggered to verify the full workflow. Each run showed a green tick but no GitHub Issue was created and no email arrived. Diagnosing this uncovered three key lessons:

  • Remote routines have no npm: the original instructions used npm outdated and npm audit. Remote cloud agents have no terminal, so these commands silently failed. The fix was switching to web API calls against the npm registry instead.
  • GitHub does not email you about your own actions: all test issues were created via the gh CLI authenticated as ghub-drew. GitHub never emails the account that performed the action. No amount of Watch settings would fix this.
  • The mention fix: adding cc @ghub-drew to the issue body triggers an email via the @mention system, which works even when the issue is on your own repo, as long as it is created by a different account (Claude's integration, not ghub-drew).

The AI also independently simulated the full scan — reading package.json from GitHub, checking the npm registry API for each package, and creating a real GitHub Issue — to confirm each step worked before blaming the routine.

🔍 Three lessons learned, all three fixed

Step 14 June 3, 2026

Claude's GitHub integration is read-only. A PAT was needed.

The routine kept completing with a green tick but never created a GitHub Issue. Looking at the run log revealed the real error: 403 Resource not accessible by integration. Claude's built-in GitHub App only has read access to issues and cannot create them.

The fix was to create a Personal Access Token (PAT) on GitHub with the repo scope, and add it to the routine instructions. The routine then calls the GitHub REST API directly using that token, bypassing the read-only integration entirely.

🔑 PAT created and added to routine instructions
⚙️
Step 15 June 3, 2026

GitHub Actions workflow added to solve the email problem

Even with the PAT working, no email arrived. The reason: the PAT authenticates as ghub-drew, and GitHub never emails you about your own actions. No watch settings or @mention in the issue body can override this.

The solution was a GitHub Actions workflow at .github/workflows/notify-on-issue.yml. Every time a new issue is opened, the github-actions[bot] automatically posts a comment mentioning @ghub-drew. Because the comment comes from a different identity (the bot, not ghub-drew), GitHub emails the owner.

The first attempt failed in 3 seconds because the workflow was missing permissions: issues: write and the explicit github-token. The fix was a one-line addition to the workflow file.

⚙️ GitHub Actions workflow live and sending emails
🎉
